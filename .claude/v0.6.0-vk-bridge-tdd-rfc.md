## 🎯 Контекст и цель

В spike `feature/vk-bot-bridge` мы за одну итерацию (2026-05-06) построили работающий **VK Bot Bridge** — альтернативный канал команд через VK сообщество, когда мобильный интернет блокирует Telegram. Spike **успешно крутится в проде на VPS уже несколько недель** под личной нагрузкой автора.

Параллельно в `origin/main` появились:
- v0.4.0 (mark-as-read, релиз)
- v0.5.0 (in progress): `BotNotifierProtocol` + `TelegramBotNotifier` с **полным набором Unit + Component + E2E тестов**

**Цель этого RFC:** **повторно реализовать VK Bridge поверх `BotNotifierProtocol` с полным TDD циклом**, используя spike как research artifact / источник реальных требований и боевых багов.

**Не цель:** портировать spike-код "как есть" с дописыванием тестов сверху. TDD = тесты ведут дизайн, не наоборот.

## 📋 Раздел 1 — Spike Findings (что узнали в проде)

> Это ключевой раздел. Без него миграция превратится в "переписать то же самое". Эти находки = **реальные требования**, найденные на эксплуатации, а не в кабинете.

### 1.1 Что подтвердилось рабочим (оставляем в архитектуре v2)

| # | Находка | Решение из spike | Сохранить? |
|---|---|---|---|
| F-01 | **VK Callback API** надёжнее Long Poll для личного использования | webhook через nginx → :8082 | ✅ да |
| F-02 | **Hummingbird 2.x** на Linux работает без сюрпризов | `from: "2.0.0"` в Package.swift | ✅ да |
| F-03 | **Плоский plain-text raw mode** (без AI) — то что нужно "в дороге" | чанки ≤ 4096 chars | ✅ да |
| F-04 | **Service mode** (long-running) обязателен — cold start TDLib 30–60 сек | CLI flag `tg-client service` | ✅ да |
| F-05 | **VK secret + whitelist by from_id** — достаточная защита для personal use | env: `VK_CALLBACK_SECRET`, `VK_BOT_OWNER_IDS` | ✅ да |
| F-06 | **Меню непрочитанных** + `/get N` (а не "сразу всё") — лучший UX | `/digest` → `/get N` | ✅ да |
| F-07 | **Iterative pagination для `/last`** — TDLib возвращает messages chronologically backward | многошаговый цикл getChatHistory | ✅ да |
| F-08 | **`/to <username>` через `searchPublicChat`** — неожиданно полезная фича | сохранить как story | ✅ да |
| F-09 | **Async Task в webhook handler** — VK retries если ответ >10 сек | моментальный "ok", обработка в фоне | ✅ да |

### 1.2 Что лажало или болело в проде (фиксим в v2)

| # | Симптом | Корневая причина | Что делаем в v2 |
|---|---|---|---|
| B-01 | **TDLib SEGV** после ~24h uptime раз в несколько дней | Continuation leak (known issue, см. CLAUDE.md) | Smoke E2E + retry/restart logic + ResponseWaiters паттерн (как в main) |
| B-02 | **Один раз забыл `VK_CALLBACK_SECRET`** → endpoint принимал случайные POST | Нет required-проверки конфига при старте | Config validation на старте, fail-fast если secret пустой |
| B-03 | **TG entities игнорируются** (bold/italic/ссылки) — пользователь ощутимо теряет контекст | RawDigestFormatter сбрасывает entities | E2E тест: проверка что bold/italic/link конвертируются (unicode bold + `[text](url)` plain) |
| B-04 | **Медиа без caption** = "пустые" сообщения, юзер не понимает что это | MessageContent: некоторые типы не маркируются | Маркеры `[🖼️ photo]`, `[🎵 audio]`, `[🎥 video]`, `[📎 file]`, `[📍 location]` |
| B-05 | **Truncate ломал Cyrillic char пополам** (не точно подтверждено, наблюдалось 1-2 раза) | Резка по байтам, не по grapheme cluster | Тест на длинной кириллической строке + `String.prefix(_:)` через `Character` |
| B-06 | **markaread не автоматический после `/get N`** — UX-боль, пользователь должен помнить | Spike сделан минимально | Опция `--auto-mark` в `/get`; либо `/get N read` суффикс |
| B-07 | **Service mode требует interactive auth первый раз** | Один баг при clean deploy | Подкоманда `tg-client auth` для одноразовой авторизации; либо чёткий runbook в DEPLOY.md |
| B-08 | **Concurrent guard работает только на одном owner** | actor mutex per-process, но если whitelist расширим — появятся race | Per-owner mutex или единый serial executor на CommandProcessor |
| B-09 | **Логов не хватало для дебага** иногда (когда команда "тихо ничего не сделала") | Логи только на error, info-уровень не везде | Audit trail: каждая команда → один INFO лог `{owner_id, cmd, decision, duration_ms}` |

### 1.3 Что НЕ делать (учли по spike)

| # | Соблазн | Почему отбрасываем |
|---|---|---|
| N-01 | "Длинные TDD циклы тормозят, опять сделаем без тестов" | Этот RFC и есть формальный отказ от такого подхода. Spike доказал value, теперь TDD |
| N-02 | "Очередь команд (FIFO) для concurrent requests" | Spike показал: "Уже обрабатываю, подожди" достаточно для personal use, очередь — overengineering |
| N-03 | "Long Poll fallback" | Webhook + nginx ни разу не лажал за время spike, не реализуем |
| N-04 | "Multi-tenant (несколько owner-сообществ)" | Spike — один owner, и в обозримом будущем тоже. Удерживаем YAGNI |
| N-05 | "AI саммари в VK ответе по умолчанию" | Spike показал что raw — это то что нужно "в дороге" (без AI задержки + затрат). Опционально через флаг — позже |
| N-06 | "Прометеус метрики" | Audit log в syslog достаточен, метрики добавим когда станут нужны |

### 1.4 Сравнение spike vs origin/main (overlap с TelegramBotNotifier)

| Аспект | Spike (BotBridge таргет) | origin/main (DigestCore/Notifiers) |
|---|---|---|
| **Куда живёт** | Отдельный таргет `BotBridge` | Внутри `DigestCore` через `BotNotifierProtocol` |
| **Транспорт** | VK Callback API → VK API | Telegram Bot API |
| **Назначение** | Двусторонний (input cmd + output reply) | Односторонний (notify пользователя дайджестом) |
| **Тесты** | ❌ нет | ✅ Unit + Component + E2E |
| **Конфигурация** | env через `BotBridgeConfig` | env через DigestCore конфиги |
| **Зависимости** | + Hummingbird (5–6 каскадных) | Только URLSession |

**Вывод по архитектуре v2:** `BotNotifierProtocol` из main — это **выходной канал** (digest → user). VK Bridge — это **двусторонний шлюз** (user → cmd → digest → user). Поэтому архитектурно они **дополняют друг друга**, а не конфликтуют:

```
VK user
   │ command
   ▼
VKWebhookServer (Hummingbird, новый)
   │
   ▼
CommandProcessor (новый, actor)
   │
   ├─ читает: ChannelMessageSource (existing)
   ├─ пишет:  VKBotNotifier: BotNotifierProtocol (новый, поверх протокола из main)
   │           ↳ под капотом VKAPIClient
   └─ markaread: TDLib viewMessages (existing)
```

Получается **VKBotNotifier — это просто ещё одна реализация уже существующего `BotNotifierProtocol`**, как `TelegramBotNotifier`. И вся механика входа (Webhook + CommandProcessor) — отдельный таргет/модуль.

## 📋 Раздел 2 — User Stories с Acceptance Criteria

> Семь stories. Каждая = одна полная итерация Outside-In TDD (E2E → Component → Unit → GREEN → REFACTOR). Приоритет = порядок реализации.

### Формат
- **Story:** As [роль], когда [условие], я хочу [результат], чтобы [цель]
- **AC (Given/When/Then):** acceptance criteria для приёмки
- **TDD entry point:** какой тест писать первым

---

### US-1: Health check / Ping (P0, первая по TDD)

**Story:** Как владелец сервиса, когда я отправляю `/ping` в VK сообщество, я хочу мгновенно получить статус бота, чтобы убедиться что сервис жив и TDLib подключён.

**AC:**
- **Given** сервис запущен и TDLib авторизован
  **When** owner шлёт `/ping`
  **Then** в течение 2 сек получает ответ `pong (tdlib: connected, uptime: 3h12m)`

- **Given** сервис запущен но TDLib потерял соединение
  **When** owner шлёт `/ping`
  **Then** получает `pong (tdlib: disconnected, last_error: ...)` БЕЗ зависания обработчика

- **Given** не-owner шлёт `/ping`
  **When** webhook принимает событие
  **Then** ответ "ok" в VK без отправки сообщения, в логах `decision=deny from_id=X`

**TDD entry point:** E2E тест с mock TDLib + mock VKAPIClient — полный путь webhook→handler→VKBotNotifier.

**Почему первая:** самая простая story, помогает обкатать всю инфраструктуру (webhook парсинг, whitelist, reply path, audit log) без бизнес-логики.

### US-2: Дайджест непрочитанных — меню (P0)

**Story:** Как владелец, когда мобильный интернет блокирует Telegram, я хочу командой `/digest` получить **меню** всех непрочитанных чатов (с unreadCount > 0), сгруппированное по типу (каналы / группы / ЛС), чтобы выбрать что читать.

**AC:**
- **Given** есть 3 канала, 2 группы, 1 ЛС с непрочитанными
  **When** owner шлёт `/digest`
  **Then** получает меню вида:
  ```
  📺 Каналы (3):
   1. Channel A — 5 unread
   2. Channel B — 12 unread
   3. Channel C — 1 unread
  👥 Группы (2):
   4. Group X — 3 unread
   5. Group Y — 7 unread
  💬 Личные (1):
   6. @alice — 1 unread
  
  Команды: /get N, /get all, /get channels|groups|dm, /last N [count]
  ```

- **Given** нет непрочитанных вообще
  **When** owner шлёт `/digest`
  **Then** получает `Нет непрочитанных сообщений ✅`

- **Given** есть >50 непрочитанных чатов
  **When** owner шлёт `/digest`
  **Then** меню режется на чанки ≤ 4096 char без потери нумерации между чанками

- **Given** TDLib недоступен (коннект упал)
  **When** owner шлёт `/digest`
  **Then** получает `Ошибка: TDLib недоступен. Проверь логи.` БЕЗ 5xx ответа в VK webhook

- **Given** owner в blacklist архивных папок
  **When** `/digest`
  **Then** архивные чаты в меню НЕ попадают (как и в существующем `fetchUnreadMessages`)

**TDD entry point:** E2E тест с mock TDLib возвращающим 6 чатов, проверка что меню сгенерировано и отправлено в VK правильным форматом.

### US-3: Загрузить чат N из меню (P0)

**Story:** Как владелец, после `/digest` я хочу командой `/get N` получить **сырой текст** всех непрочитанных сообщений выбранного чата, чтобы прочитать их в VK.

**AC:**
- **Given** меню `/digest` отправлено, в текущей session_state хранится список чатов
  **When** owner шлёт `/get 3`
  **Then** получает сообщения чата #3 в формате:
  ```
  📺 Channel C
  
  [12:34] Message 1 text...
  [12:45] Message 2 text...
  ```
  с правильным сохранением **bold/italic/links** (unicode + plain `[text](url)`).

- **Given** меню не было отправлено в текущей сессии
  **When** owner шлёт `/get 3`
  **Then** получает `Сначала вызови /digest, чтобы построить меню.`

- **Given** N выходит за пределы меню
  **When** `/get 99`
  **Then** получает `В меню только 6 чатов. Выбери 1–6 или /digest заново.`

- **Given** chat #3 содержит фото без подписи
  **When** `/get 3`
  **Then** в выводе появляется `[🖼️ photo]` (маркер), а не пустое место

- **Given** owner шлёт `/get all`
  **When** обработка
  **Then** все чаты из меню по очереди, разделённые `--- N. <name> ---`

- **Given** owner шлёт `/get channels` (или `groups` / `dm`)
  **When** обработка
  **Then** только чаты этой категории

- **Given** owner шлёт `/get 3 read`
  **When** обработка
  **Then** после доставки чат помечается как прочитанный через TDLib `viewMessages` (опционально — закрывает B-06)

**TDD entry point:** Component тест на форматтере (с mock messages) → E2E тест на полном пути.

### US-4: История сообщений чата (P1)

**Story:** Как владелец, я хочу командой `/last N [count]` получить **последние count сообщений** чата #N (включая прочитанные), чтобы поднять контекст по диалогу из VK.

**AC:**
- **Given** меню есть, count не указан
  **When** owner шлёт `/last 3`
  **Then** получает 20 последних сообщений (default)

- **Given** count = 100
  **When** `/last 3 100`
  **Then** получает 100 сообщений (возможно через несколько TDLib итераций — getChatHistory отдаёт батчами по 100)

- **Given** count > 500
  **When** `/last 3 1000`
  **Then** получает `count ограничен 500. Используй /last N 500.`

- **Given** в чате <count сообщений
  **When** `/last 3 1000`
  **Then** возвращает все доступные + хвостовая строка `(ещё нет данных)`

**TDD entry point:** Component тест на iterative pagination logic с mock TDLib batches.

### US-5: Ответить в чат через VK (P1)

**Story:** Как владелец, я хочу командой `/reply N <текст>` отправить сообщение в Telegram-чат #N от своего имени, чтобы участвовать в диалоге не открывая Telegram.

**AC:**
- **Given** меню есть, чат #3 — ЛС с @alice
  **When** owner шлёт `/reply 3 Привет!`
  **Then** в TG отправляется "Привет!" в чат с @alice через TDLib `sendMessage`,
  в VK owner получает `✅ Отправлено в Channel/Group/DM "Channel C"`

- **Given** текст содержит спецсимволы или эмодзи
  **When** `/reply 3 Йоу 🚀 #тест @bob`
  **Then** TDLib отправляет как plain text без интерпретации markdown

- **Given** sendMessage упал (rate limit, чат удалён)
  **When** `/reply 3 ...`
  **Then** owner получает `❌ Не удалось отправить: <причина>` с error из TDLib

**TDD entry point:** E2E тест с mock TDLib `sendMessage` (success + failure paths).

### US-6: Сообщение по @username (P2)

**Story:** Как владелец, я хочу командой `/to <username> <текст>` отправить сообщение **любому** пользователю Telegram по @username, даже если у меня с ним нет существующего чата.

**AC:**
- **Given** @bob существует и принимает сообщения
  **When** owner шлёт `/to bob Здарова`
  **Then** через `searchPublicChat` находит chat_id и шлёт через `sendMessage`,
  в VK получает `✅ Отправлено @bob`

- **Given** @nonexistent не существует
  **When** `/to nonexistent привет`
  **Then** owner получает `❌ Пользователь @nonexistent не найден`

- **Given** @bob закрыл сообщения от незнакомцев
  **When** `/to bob привет`
  **Then** owner получает `❌ @bob запретил сообщения от незнакомцев` (TDLib error)

- **Given** username с/без @ префикса
  **When** `/to @bob привет` или `/to bob привет`
  **Then** одинаково работают (нормализация)

**TDD entry point:** Component тест на нормализацию username + E2E с mock searchPublicChat.

### US-7: Отметить чат как прочитанный (P2)

**Story:** Как владелец, я хочу командой `/read N` пометить чат #N как прочитанный (без открытия мессенджера), чтобы в `/digest` он больше не появлялся.

**AC:**
- **Given** меню есть, чат #3 имеет 5 непрочитанных
  **When** owner шлёт `/read 3`
  **Then** через TDLib `viewMessages` помечает все непрочитанные как viewed,
  в VK получает `✅ Channel C помечен прочитанным (5 сообщений)`

- **Given** чат уже без непрочитанных
  **When** `/read 3`
  **Then** owner получает `✅ Channel C уже прочитан`

- **Given** TDLib недоступен
  **When** `/read 3`
  **Then** owner получает `❌ TDLib недоступен`

**TDD entry point:** E2E с mock TDLib viewMessages.

### 3.3 Интеграционные / cross-cutting тесты

| Тест | Тип | Что проверяет |
|---|---|---|
| **VK secret missing in env** | E2E (config) | приложение НЕ стартует, exit code != 0, лог-сообщение (закрывает B-02) |
| **Confirmation handshake** | E2E | POST `{type:"confirmation"}` → возвращаем `VK_CONFIRMATION_TOKEN` plain text |
| **Concurrent /digest** (две одновременные команды от owner) | E2E | вторая получает "Уже обрабатываю, подожди" БЕЗ запуска второго fetchUnreadChats |
| **Webhook returns 200 даже при 5xx внутри** | E2E | отдаём "ok" моментально, ошибка в фоне → лог error (закрывает паттерн F-09) |
| **Audit log** для каждой команды | E2E | один INFO лог `cmd=X owner=Y decision=Z duration_ms=N` (закрывает B-09) |
| **Cyrillic + emoji в truncate** | Unit | `String.prefix(_:)` через grapheme cluster (закрывает B-05) |
| **Не-owner получает silent ok** | E2E | отвечаем "ok" в VK, **не отправляем** ничего юзеру, лог `decision=deny` |

### 3.4 Что НЕ покрываем тестами (явно)

| Что | Почему |
|---|---|
| Реальный VK API (live API ключ) | Spike доказал что API работает; CI не должен зависеть от внешних |
| Реальный TDLib (без mock) | E2E с реальным TDLib в main уже есть, дубль не нужен; для нового кода mock достаточен |
| Производительность под нагрузкой | Personal use, ~10 команд/день, не нужно |
| HTTPS termination (nginx) | Системное, тестим вручную smoke на сервере |
| systemd lifecycle | Не покрываем кодом, только runbook'ом |

## 📋 Раздел 6 — TDD Pipeline

> Outside-In, **per-story цикл**. Не двигаемся к US-(N+1), пока US-N не GREEN + REFACTORed. Это значит: 7 stories = 7 циклов = 7 PR (или 7 пачек коммитов в ветке).

### 6.1 Шаблон одной итерации (per-story)

```
┌──────────────────────────────────────────────────────────────┐
│  US-N итерация (1–3 дня каждая)                              │
├──────────────────────────────────────────────────────────────┤
│  STEP 0  Architecture-First spike                            │
│         → если новые зависимости, новые протоколы — открыть   │
│            мини-RFC внутри этого документа (раздел 5.4)       │
│  STEP 1  E2E test (RED)                                      │
│         → описывает observable behavior из AC story          │
│         → mock'и: TDLib + VK API                             │
│  STEP 2  Component drop-in                                   │
│         → выявляются collaborators (Formatter, Parser, ...)   │
│         → tests пишем ДО реализации                          │
│  STEP 3  Unit tests                                          │
│         → парсеры, форматтеры, модели — pure functions       │
│         → быстрые (<10ms each)                               │
│  STEP 4  GREEN — minimal code                                │
│         → fakeit'ить если нужно, но всё что fake → TODO       │
│  STEP 5  REFACTOR                                            │
│         → extract, rename, kill duplication                  │
│         → tests stay green throughout                        │
│  STEP 6  Smoke run на dev VPS (для P0 stories)               │
│         → VK команда → реальный TG → проверка глазами         │
│  STEP 7  Commit batch + PR (or merge to feature/vk-bridge-tdd)│
└──────────────────────────────────────────────────────────────┘
```

### 6.2 Roles per step (из ROLES.md main)

| STEP | Роль | Что делает |
|---|---|---|
| 0 | **Architect** | Согласовать структуру модулей и протоколов с пользователем ДО кода |
| 1 | **Testing Architect** | E2E дизайн + mock стратегия для story |
| 2 | **Testing Architect** | Component тесты — выявление collaborators |
| 3 | **Testing Architect** | Unit тесты — pure logic (parsers, formatters) |
| 4 | **Swift Developer** | Минимальный код для GREEN |
| 5 | **Swift Developer** | Refactor с защитой тестами |
| 6 | **AI-Assisted Developer** | Smoke + контекст-проверка на сервере |
| 7 | **Swift Developer** | Атомарные коммиты, PR description |

### 6.3 Research-First чек (для US-1)

US-1 — первая story → новый код для нового таргета. **Обязателен Research-First** (см. TESTING.md):

- ✅ Spike на Hummingbird + linux + Swift 6 — уже **сделан** (это и есть наш `feature/vk-bot-bridge`). RFC не дублирует обучение
- ✅ VK Callback API — изучен в spike, `vk-bot-bridge-rfc.md` имеет полный контракт
- ⚠️ **Не done:** `XCTHBApplication.test` testing helper в Hummingbird 2.x — нужен мини-spike (~30 мин) на изоляцию routes для Component тестов
- ⚠️ **Не done:** интеграция `swift-service-lifecycle` для graceful shutdown — мини-spike (~1ч)

### 6.4 Anti-pattern: чего избегаем (из TESTING.md retro)

| Соблазн | Почему вредно | Что делаем |
|---|---|---|
| Mock >100 строк (например, fake VK API server in-process) | Mock сам становится bug source, эффект "тестирую mock" | `MockHTTPClient` → table-driven scripted responses, ≤30 строк. Ассертим request snapshot |
| Параллельные тесты на shared TDLib state | Race conditions в самих тестах | Каждый тест → свой `MockTDLibClient` instance |
| Закомментированный тест | Легко забыть, накапливается tech debt | `#if false` запрещён. Только `XCTSkip` с reason |
| Тесты на implementation detail | Пере-mocking, fragile | E2E через protocol boundary, не через приватные функции |
| "Пишу код, потом обмажусь тестами" | Мы это уже сделали в spike — больше не делаем | RED→GREEN строго |

### 6.5 Definition of Done (per story)

Story закрыта если:
- [x] AC из раздела 2 — все Given/When/Then проходят
- [x] Все 3 уровня тестов на месте (E2E + Component + Unit где применимо)
- [x] Coverage на новый код ≥ 80% (line + branch)
- [x] `swift test 2>&1` GREEN на Linux (build-clean.sh)
- [x] `swift test --sanitize=thread 2>&1` GREEN (TSan)
- [x] Smoke на dev VPS пройден для P0 stories (US-1, US-2, US-3)
- [x] Audit log на команду виден в syslog (B-09)
- [x] Atomic commits (Sources / Tests / Docs отдельно)

### 6.6 Параллелизация (если нужна скорость)

Stories внутри **одной фазы** обычно зависят (US-2 строит меню, US-3 его читает). Между фазами — сильно меньше связности. **Возможность параллели:** US-5/US-6/US-7 в Phase 3 — независимые, можно делать в любом порядке или параллельно (ветки feature/vkbridge-us5 etc, потом merge). Но для одного разработчика — последовательно проще.

sudo systemctl disable tg-client-v06.service

# держим backup spike-binary

## 📋 Раздел 10 — Risks + Mitigations

> Что может пойти не так и что мы заранее продумали.

### 10.1 Технические риски

| # | Риск | Вероятность | Impact | Mitigation |
|---|---|---|---|---|
| **R-01** | TDLib SEGV (B-01, continuation leak) | 🟡 средняя | 🔴 высокий (сервис падает) | Использовать `ResponseWaiters` паттерн уже принятый в main; systemd `Restart=always` с throttle; добавить healthcheck endpoint для алерта |
| **R-02** | SwiftPM hang issue #9441 на Linux | 🟡 средняя | 🟡 средний (билды вешаются) | `./scripts/build-clean.sh` уже работает; новые deps (Hummingbird) не должны увеличить кол-во SwiftPM-конфликтов; мониторим issue #9441 |
| **R-03** | Hummingbird breaking change в minor version | 🟢 низкая | 🟡 средний | Pin `from: "2.0.0"` (semver guarantees), CI проверяет совместимость, контракт через protocol тонкий |
| **R-04** | swift-service-lifecycle несовместим с TDLib lifecycle | 🟢 низкая | 🟡 средний | Phase 1 включает мини-spike (~1ч) на интеграцию; fallback — простой `Task { await server.run() }.wait()` |
| **R-05** | TDLib `viewMessages` имеет race condition при auto-mark + `/get` | 🟡 средняя | 🟡 средний | E2E тест с проверкой unreadCount после `/get N read`; если race — auto-mark делать через очередь |
| **R-06** | VK Callback API меняет схему JSON | 🟢 низкая | 🔴 высокий | `VKModels` через optional fields; AdditionalProperties decoding; алерт если 5+ unknown event types за час |

### 10.2 Операционные риски

| # | Риск | Вероятность | Impact | Mitigation |
|---|---|---|---|---|
| **R-07** | Disk pressure на VPS (86% used) | 🔴 высокая | 🔴 высокий (билд упадёт) | Перед каждой Phase: `du -sh .build` + cleanup; рассмотреть migration на больший VPS до Phase 2; не держать debug + release одновременно |
| **R-08** | Cutover downtime (между остановкой spike и стартом v0.6.0) | 🟡 средняя | 🟡 средний (юзер не получит дайджест 1-2 минуты) | Cutover в окно низкой нагрузки; параллельный деплой v06 минимизирует окно; rollback скрипт готов (раздел 8.3) |
| **R-09** | Spike в проде падает между Phase 2 и Phase 3 | 🟡 средняя | 🔴 высокий (сервис недоступен) | План B: ускоренный cutover на v0.6.0-beta (без Phase 3 команд — `/last`, `/reply`, `/to`, `/read` временно отказывают) |
| **R-10** | TDLib auth ломается при cutover (новый stateDir не подхватился) | 🟢 низкая | 🔴 высокий (нужна re-auth с phone+code) | Использовать **тот же** `TDLIB_STATE_DIR` что в spike; backup state dir перед cutover |
| **R-11** | nginx/cert обновится и сломает webhook | 🟢 низкая | 🟡 средний | Не трогаем nginx config во время миграции; certbot renewal проверен на текущей ноде |

### 10.3 Процессные риски

| # | Риск | Вероятность | Impact | Mitigation |
|---|---|---|---|---|
| **R-12** | TDD цикл занимает существенно дольше estimate | 🟡 средняя | 🟡 средний | Per-phase **time-box**: если Phase 1 > 7 дней — пересматриваем стратегию (может быть упрощаем DI, или сокращаем тесты), не переносим slip на Phase 2/3 |

## 📚 Открытые вопросы перед стартом Phase 1

> Эти вопросы должен закрыть пользователь до того как начнётся Phase 1 implementation.

1. **Branch strategy подтверждаем?** Новая ветка `feature/vk-bridge-tdd` от свежего `origin/main`, spike-ветка остаётся как reference.

2. **Параллельный VK community для тестов или тот же?** Если тот же — `/digest` команды от owner будут идти на оба binary одновременно (когда v0.6.0-beta параллельно). Лучше тестовое сообщество.

3. **VPS upgrade до старта Phase 2?** При 86% диска и 1 CPU — Phase 2 builds могут стать болью. Решение: больший VPS / cleanup `.build` каждый раз / docker.

4. **Time budget на спайки в Phase 1?** Hummingbird testing helpers (~30 мин) + service-lifecycle (~1ч) — допустимо в общем эстимейте 3-5 дней?

5. **Auto-mark-as-read default — `false` или `true`?** Spike-режим — `false` (надо вручную /read). Закрытие B-06 — добавить опцию. Но default — какой? Я склоняюсь к `false` (consent), но можно `true` (UX-first).

6. **Удаляем `/to_alena` shortcut или оставляем?** Это hack из spike. Аргумент за: персональный продукт, удобно. Против: специальный case в коде.

7. **Деплой на сервер делает Claude или ты руками?** Сейчас Claude имеет sudo доступ, может всё сделать. Но cutover лучше вручную для контроля.
