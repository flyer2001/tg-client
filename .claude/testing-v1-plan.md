# План: тестовая архитектура к v1.0.0

> Создан 2026-10-16. Основа — разбор книги М. Рубанова «Про тестирование на iOS» (приватный разбор — в `comms/docs`,
> цитаты из платной книги в публичный репо не кладём) против аудита проекта.
> Порядок: итерации маленькие, после каждой — замер и решение «оставляем / откатываем».

## Цель

1. Тесты ловят то, что сейчас ловят только живые прогоны (2026-10-15/16: фото без подписи, форумы — 340 зелёных тестов
   их пропустили).
2. Тесты читаются и пишутся быстрее: DSL вместо разбора сырого JSON, понятное место падения.
3. Документы о тестах правдивы и коротки — их читает ИИ, противоречия = неверный код.
4. Гипотеза H-PF: библиотеки Point-Free облегчают жизнь настолько, что окупают зависимость.

Мутационная проверка (на каждой итерации, где меняем тесты): сломать боевой код в 2-3 местах — тест обязан упасть
**на строке теста** с понятным сообщением. Тест, который не упал, — не тест.

## Как не сломать

- Одна итерация = свои коммиты (Sources / Tests / docs раздельно), откат — `git revert` её коммитов.
- Перед каждым коммитом: полный набор зелёный 3 прогона подряд на ubuntu-home; число тестов не уменьшилось
  (кроме явно удалённых дублей — с перечнем в коммите).
- Миграция тестов по одному suite: старый и новый стиль живут рядом, пока suite не переведён целиком.
- Боевой код меняем только там, где этого требует итерация (И5 — время, И6 — запись трафика); деплой службы —
  только после полного E2E (`get-summary` → `read` → пусто) на реальных чатах с разрешения Sergey.
- Зависимости: точная версия (`exact:`), не моложе 2 недель, не старше 6 месяцев; тестовые — только в тестовые таргеты.

## Итерации

### И0. Спайки и база — сделано 2026-10-16

- База: 10 прогонов, 0 падений, ~5 с; component-набор 3.0 с.
- Спайк Point-Free на Linux / Swift 6.4 (`~/spikes/pf-deps` на ubuntu-home): swift-dependencies 1.17.1, custom-dump 1.7.3,
  snapshot-testing 1.19.6 (InlineSnapshotTesting → swift-syntax), swift-clocks 1.1.1, concurrency-extras 1.4.2
  (1.4.3 вышла 2026-10-14 — моложе 2 недель). Чистая сборка 54 с, 488 МБ, 0 ворнингов; работают `expectNoDifference`
  (дифф), inline-снепшот (пишет ожидаемое в исходник), `TestClock`, `withMainSerialExecutor`, `reportIssue`.
- Подвох: inline-снепшот записывается в исходник на ubuntu-home → следующий `rsync --delete` с VDS его затрёт.
  Нужен шаг «забрать Tests/ обратно» после записи.
- `scripts/test-metrics.sh` — метрики таблицы одной командой; чистая сборка проекта с тестами — 17 с (154 МБ).
  Значит swift-syntax (InlineSnapshotTesting) — это ×4 к чистой сборке: учесть в решении И4.2.

### И1. Правда в документах (P1)

TESTING.md переписать коротко (~100 строк): карта уровней (что проверяем → тип теста), таксономия даблов
(dummy / stub / spy / fake / mock — наш `MockTDLibFFI` = fake + spy), правила (fake только на границе, DSL над ним,
незастабленное падает на строке теста, время — зависимость, `sut` собирается одной функцией). Ретро-статистику — в archived.
Исправить: ROLES (чек-лист «мок на каждый метод»), CLAUDE.md (битый якорь), CI (`swift test | head`), агент
`tdlib-integration` (TDLibClient не actor; раздел про тесты), мёртвые скрипты, перегенерировать DocC.
**Сделано 2026-10-16.** DocC-страницы тестов — локальные (в `.gitignore`), устаревшими в репо не были; автоссылка
на несуществующий `MockTDLibFFITests` убрана из генератора. E2E-скрипты и SwiftLint-хук — в И7.
Проверка: повторный аудит субагентом → 0 противоречий.

### И2. Незастабленный запрос падает на строке теста (P1)

Спайк сначала: `receive()` фейка крутится не в задаче теста — увидит ли Swift Testing `Issue.record` оттуда?
Вариант: фейк отвечает TDLib-ошибкой `{"@type":"error","message":"unmocked <type>"}` + `reportIssue` с
`sourceLocation`, захваченным при создании сценария. Критерий: мутационная проверка — забытый стаб даёт падение
с именем запроса и строкой теста, процесс не падает.
**Сделано 2026-10-16.** `MockTDLibFFI(sourceLocation:)` / `MockHTTPClient(sourceLocation:)` захватывают строку создания;
незастабленное → `Issue.record` там + ошибка клиенту (`fatalError` в TestHelpers 17 → 0). `send()` фейка вызывается
из `Task` внутри `sendAndWait` — task-local текущего теста наследуется, issue привязывается к тесту. Мутация
(убран стаб `viewMessages` в `BrokerTests.read`): раньше — падение всего прогона, теперь — issue на строке фейка
с подсказкой `добавь mockResponse(forRequestType: "viewMessages", …)`, остальные тесты выполнились.

### И3. DSL над фейком TDLib (P1)

Слой поверх `MockTDLibFFI`: `givenChat(…)`, `givenHistory(…)`, `givenForum(…)` (для форумов), `expectViewed(chat:upTo:)`,
`makeBroker()/makeCollector()` как единая сборка `sut`; ассерт-хелперы с `sourceLocation`. Перевести
`BrokerTests`, `SummaryCollectorTests`, `CursorApplyTests`. Метрики: строк на тест, разбор сырого JSON, мутационная проверка.

**Сделано 2026-10-16.** `Tests/TestHelpers/TDLibScenario.swift`: `givenChat/givenHistory/givenMarkAsReadSucceeds`,
`expectViewed/expectNothingViewed` (с `sourceLocation`), `makeCollector()/makeBroker()`; в фейке — история по `chat_id`
(`mockHistory`), а не FIFO по типу (при параллельной загрузке чатов история могла уйти не тому чату). Переведены
`BrokerTests`, `SummaryCollectorTests`, `CursorApplyTests`: 248 → 204 строки, сырой JSON 9 → 0. Мутации 3/3 убиты,
падение — на строке теста с понятным diff (`viewed() → [123: [104]]`, `expected → [123: [105]]`).
Остальные suite (`ChannelMessageSourceTests` 753 строки и др.) — переводим при касании, не отдельной итерацией.

→ **Форумы** — сделаны 2026-10-16 по TDD на этом DSL: `givenForum`, ответы фейка по параметрам запроса.
Тест сразу поймал реальную проблему: Bool в новых моделях на Linux приходит числом после JSONSerialization.
E2E на реальном форуме: 4 темы помечены, остальные чаты не тронуты.

### И4. Гипотеза H-PF (Point-Free) — по шагам, каждый со своим решением

1. Тестовые `CustomDump` + `ConcurrencyExtras`: `expectNoDifference` вместо пачек `#expect`, `withMainSerialExecutor`
   вместо `sleep` в `AuthenticationFlowTests`/`ProxyStartupTests`. Оставляем, если: убраны sleep'ы и падения читаются
   лучше на мутационной проверке; сборка +≤ 20 с.
2. `InlineSnapshotTesting` — снимок последовательности запросов в TDLib и JSON `get-summary`. Цена: swift-syntax
   (+~40 с чистой сборки) и шаг «забрать Tests/ обратно». Оставляем, если снепшоты заменяют ≥ 30% ручных проверок
   запросов без потери понятности.
3. `swift-dependencies` в боевом коде — по умолчанию **нет**: время передаём параметром `any Clock<Duration>`
   (stdlib), `TestClock` из swift-clocks — только в тестах. Пересмотреть, если зависимостей для подмены станет > 3.

Итог гипотезы — таблица «что дала / сколько стоила» в CHANGELOG и вердикт.

**Шаг 1 — сделан 2026-10-16 (эксперимент на копии, затем в репо):**

| Библиотека | Что дала | Цена | Вердикт |
|---|---|---|---|
| CustomDump 1.7.3 + IssueReportingTestSupport (swift-issue-reporting 2.1.1) | дифф `− name: "General!" / + name: "General"` вместо обрезанной строки `#expect` | чистая сборка 17 → 19 с, `.build` +35 МБ | **берём** (только тесты) |
| ConcurrencyExtras | ничего: 3 `sleep` в AuthenticationFlowTests устарели сами (ResponseWaiters буферизует ранний update, 0/30 + 0/10 без sleep), остальные — реальное время (И5) или цикл receive на DispatchQueue, которым serial executor не управляет | — | **не берём** |

Подвох: без `IssueReportingTestSupport` `expectNoDifference` под Swift Testing тест **не роняет**. swift-issue-reporting 2.1.2
вышла 2026-10-13 (< 2 недель) — закреплена 2.1.1. Следующий шаг H-PF — снепшоты (И4.2), решать после И5.

### И5. Время как зависимость (P2)

`ChannelMessageSource` (пагинация, сбор updates), `RetryHelpers`, `MarkAsReadService` таймауты → `any Clock<Duration>`.
Тесты — `TestClock`/`ImmediateClock` (или свой, если H-PF отвергнута). Метрики: component-набор < 0.5 с,
`sleep` ≤ 2, окна по `ContinuousClock` в `RetryHelpersTests` убраны.

**Сделано 2026-10-16.** Вместо `Clock` — уже существующий в проекте паттерн `sleep:`-замыкания (`VKLongPollClient`),
правило 0 «переиспользуй». `withRetry(sleep:)`, `TelegramBotNotifier(sleep:)`, `DigestOrchestrator(sleep:)`;
`SleepRecorder` вынесен в TestHelpers, `DelayRecorder` удалён. Таймаут попытки — на реальных часах (верхняя граница).
Итог: component-набор 3.006 → 0.062 с, unit 0.459 → 0.161 с, полный прогон ~5 → ~1.9 с; `sleep` 16 → 11
(оставшиеся — фейк TDLib, висящий long poll, E2E, ожидание в ProxyStartupTests, «висеть до таймаута»; цель ≤ 2
переформулирована: без реального ожидания в логике теста). Мутация «линейный бэкофф» выжила при 3 попытках
(100, 200 = 2^n) → тест расширен до 4 попыток, мутант убит. `swift-clocks`/`TestClock` (H-PF) не понадобились.

### И6. Контрактные тесты: запись и воспроизведение трафика TDLib (P2)

- `RecordingTDLibFFI` — обёртка над настоящим FFI, пишет JSONL (запрос / ответ / update, по `@extra`) при живом прогоне.
- Анонимизатор: тексты, имена, телефоны, username → заглушки; id и структура сохраняются. **Сырые записи — только
  локально на ubuntu-home, в публичный репо — только анонимизированные** (репо публичный, сообщения чужие).
- `ReplayTDLibFFI` — отдаёт записанное по типу и порядку; режимы строгий / живой.
- Проверки: инварианты (курсор ≥ last_read, у каждого чата unread > 0 …) в обоих режимах, точные значения — только в воспроизведении.
- **Приёмка:** оба живых бага (фото без подписи, форум) воспроизводятся тестом из записи.

### И7. E2E включаются через env (P2)

`.disabled` → `.enabled(if: TG_E2E == "1")`; `get-summary` через сокет при работающей службе, проверка инвариантов;
цикл с `read` — только при `TG_E2E_WRITE=1` (меняет реальный аккаунт). Запуск — перед релизом. Починить
`run-e2e-*.sh` (запускают выключенный тест), `install-git-hooks.sh` (SwiftLint отключён), удалить мёртвое.
